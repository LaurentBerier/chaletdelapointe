The chalet uses Supabase Auth for identity and the Express API for website permissions. Email confirmation creates a member profile. Only owners can book or see reservation names. Only the super administrator can change account access, manage the chalet and publish articles. Self-registration never creates an owner or administrator.

On an existing chalet database, apply the two SQL files in migrations in order, once, after the base Drizzle schema and reservation invariants. The second file imports the four original articles at their original URLs. Set the first super administrator directly in the database after checking the existing confirmed Auth UUID, email and linked owner profile. There is no web endpoint for granting that role. Use a separate database administrator for migrations; the web role does not need to write the administrator flag.

For hosted Auth, enable email sign-ups, require confirmation, allow the site's /connexion redirect, and configure SMTP. The French confirmation, magic link and recovery emails are in templates. The local Supabase config uses the same templates.

For a regression check, start a disposable local chalet stack with email confirmation, Mailpit, a configured chalet and booking SMTP. Export DATABASE_URL, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, CHALET_TEST_SITE and CHALET_TEST_MAILPIT and run `node lib/db/scripts/test-account-lifecycle.cjs`. This checks signup, password login and recovery, member and owner access, protected administration, publishing, name visibility, approval and reservation edits. It only accepts loopback services and removes its test records.
