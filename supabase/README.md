The chalet uses Supabase Auth for identity and the Express API for website permissions. Email confirmation submits an application; only administrator approval opens the member area. The declared relationship never assigns a role or permissions. Only confirmed owners see reservation names. Booking can be granted independently of the role. Members can request permission to book from their profile or the calendar. Only the super administrator can approve that access; it does not reveal others’ reservation names or grant approval powers. Individual stays still require a separate approval. Only the super administrator can change account access, manage the chalet and publish articles. Self-registration never creates an owner or administrator.

On an existing chalet database, apply the SQL files in migrations in order, once, after the base Drizzle schema and reservation invariants. The second file imports the four original articles at their original URLs. Set the first super administrator directly in the database after checking the existing confirmed Auth UUID, email and linked owner profile. The security panel reads only a password-presence flag maintained by Auth triggers; application users and the web role never read Auth credentials. There is no web endpoint for granting the administrator role. Use a separate database administrator for migrations; the web role does not need to write the administrator flag.

For hosted Auth, enable email sign-ups, require confirmation, allow the site's /connexion redirect, and configure SMTP. The French confirmation, magic link and recovery emails are in templates. The local Supabase config uses the same templates.

For a regression check, start a disposable local chalet stack with email confirmation, Mailpit, a configured chalet and booking SMTP. Export DATABASE_URL, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, CHALET_TEST_SITE and CHALET_TEST_MAILPIT and run `node lib/db/scripts/test-account-lifecycle.cjs`. This checks signup, password login and recovery, member and owner access, protected administration, publishing, name visibility, approval and reservation edits. It only accepts loopback services and removes its test records.

For the optional passwordless invitation check, also supply CHALET_TEST_AUTH_ADMIN_KEY from the local Supabase test stack. Never use production credentials for this check.

Super-admin cancellations release the dates, write one audit entry and queue one email to the booker in the same transaction. The site attempts delivery immediately; the existing daily mail job also retries unsent booking notices. No database migration is needed for this feature.

Apply 202611150005 before deploying the owner calendar. It assigns each owner a permanent color slot when their role is granted. Signed-in owners can see the booker’s name on both pending and confirmed stays and, for owner bookings, their color. The public and non-owner calendars contain neither field. Nights are occupied from arrival up to, but not including, checkout. The calendar marks the departure day; a new stay can start on that date.

Reservation access mail is separate from stay approvals. Migration 202611150002 queues the notification with the access change. The website sends it using SMTP_URL, BOOKING_EMAIL_FROM and WEBSITE_URL (the canonical public origin). Requests go to active super administrators; the member receives the decision. The signed-in admin must explicitly accept or refuse the referenced request. Configure CRON_SECRET as a Vercel production secret for the daily retry at /api/jobs/access-mail. The admin dashboard also retries due mail while open.

For the account-review rollout apply 202611150003 first, deploy the registration-aware API and UI, then activate new applications with 202611150004. Existing members keep their actual roles and booking rights. Self-signups require review even when using an older client. The admin can assign roles, booking permission and owner committee rights on approval or later, under Comptes et accès. The registration and decision emails share the access-mail outbox and retry job. Update the hosted Auth confirmation body from supabase/templates/confirmation.html.

To run the desktop and mobile calendar regression on the same disposable stack, set CHALET_TEST_SITE, SUPABASE_URL, DATABASE_URL, CHALET_TEST_AUTH_ADMIN_KEY, and CHALET_TEST_CHROMIUM (a local Chromium executable). Make puppeteer-core available to Node, for example via NODE_PATH, then run `node lib/db/scripts/test-calendar-ui.cjs`. The test uses temporary profiles and the 18th through the end of next month on the local test chalet; leave those dates free.
