The chalet uses Supabase Auth for identity and the Express API for website permissions. Email confirmation creates a member profile. Owners can book and see reservation names. Members can request permission to book from their profile or the calendar. Only the super administrator can approve that access; it does not reveal others’ reservation names or grant approval powers. Individual stays still require a separate approval. Only the super administrator can change account access, manage the chalet and publish articles. Self-registration never creates an owner or administrator.

On an existing chalet database, apply the SQL files in migrations in order, once, after the base Drizzle schema and reservation invariants. The second file imports the four original articles at their original URLs. Set the first super administrator directly in the database after checking the existing confirmed Auth UUID, email and linked owner profile. The security panel reads only a password-presence flag maintained by Auth triggers; application users and the web role never read Auth credentials. There is no web endpoint for granting the administrator role. Use a separate database administrator for migrations; the web role does not need to write the administrator flag.

For hosted Auth, enable email sign-ups, require confirmation, allow the site's /connexion redirect, and configure SMTP. The French confirmation, magic link and recovery emails are in templates. The local Supabase config uses the same templates.

For a regression check, start a disposable local chalet stack with email confirmation, Mailpit, a configured chalet and booking SMTP. Export DATABASE_URL, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, CHALET_TEST_SITE and CHALET_TEST_MAILPIT and run `node lib/db/scripts/test-account-lifecycle.cjs`. This checks signup, password login and recovery, member and owner access, protected administration, publishing, name visibility, approval and reservation edits. It only accepts loopback services and removes its test records.

For the optional passwordless invitation check, also supply CHALET_TEST_AUTH_ADMIN_KEY from the local Supabase test stack. Never use production credentials for this check.

Reservation access mail is separate from stay approvals. Migration 202611150002 queues the notification with the access change. The website sends it using SMTP_URL, BOOKING_EMAIL_FROM and WEBSITE_URL (the canonical public origin). Requests go to active super administrators; the member receives the decision. The signed-in admin must explicitly accept or refuse the referenced request. Configure CRON_SECRET as a Vercel production secret for the daily retry at /api/jobs/access-mail. The admin dashboard also retries due mail while open.
